## Status: Not started. This is a scoped investigation + plan, not a partial implementation.

## Where this fits

The S10 action-family rollout (`docs/superpowers/plans/2026-09-06-code-quality-cleanup.md`, `docs/review/action-runtime-progress.md`) is now complete for `actions-v1`: `messenger.send`, `image.generate`, `social.post`/`comment`, `bank.transfer`, `note.write`, `assistant.chat` are all model-authorable end to end (see `docs/handoff/2026-09-12-note-write.md` for the full session trail). `bank.transfer` and `note.write` are also now live on `staged-v1` (same handoff doc, its final section). **The one remaining gap in the whole rollout is `assistant.chat` on `staged-v1`.**

**Important framing note, corrected by the user mid-rollout**: do not treat any one family (bank.transfer was the past example) as architecturally special or "the hard one." Investigate each on its own merits. In this specific case, `assistant.chat` genuinely does need new compiler infrastructure that `bank.transfer`/`note.write` did not — that is a real, checkable technical difference (detailed below), not a narrative pattern to default into.

## The actual gap (confirmed, with exact locations)

`assistant.chat`'s creative content is `messages: Array<{role: 'user'|'assistant', text: string}>`, 2–8 entries (1–4 exchanges), strictly alternating starting with `user` (see `src/actions/contracts.ts`'s `AssistantChatAction`/`AssistantChatMessage`, and `src/actions/compileReply.ts`'s `assistantChat()` compiler for the exact validation rules already implemented and tested for `actions-v1`).

The staged-workflow compiler cannot express this today, for two independent, concrete reasons — both confirmed by reading the source, not inferred:

1. **`src/staged-workflow/compileTurnPlan.ts:187`**: `if (step.kind === 'generate-content') check(!!step.instruction && step.output === 'text', 'Content writers require instructions and text output.');` — every `generate-content` step is hard-required to output exactly `'text'`. There is no way today to declare a step that produces anything else.
2. **`src/staged-workflow/contracts.ts:2`**: `export type VariableKind = 'text' | 'facts' | 'entity' | 'artifact' | 'receipt' | 'plan';` — there is no kind that represents "a list of role/text pairs." `src/staged-workflow/contentRunner.ts`'s `createStagedContentAdapter` (the actual LLM-calling adapter) is typed to always return `Promise<string>` (see `StagedSchedulerAdapters['generateContent']` in `scheduler.ts`), and `scheduler.ts:78`'s `outputValueForStage` only knows how to wrap a raw string into `{kind:'text', text: result}` — never anything structured, for a `generate-content` step.

Contrast with why `note.write` *did* fit without new infrastructure: its two creative fields (`title`, `body`) are each independently a single string, so it could be modeled as **two separate `generate-content` steps**, each still outputting plain `text`, consumed positionally by one `execute-action` step (see `recipeInventory.ts`'s `note.write` branch in `stagedRecipeDefinitions()`, and `stagedActionAdapter.ts`'s `textInputAt` helper). `assistant.chat` can't use that trick because the *number* of messages is itself model-decided (2, 4, 6, or 8) — you can't declare a fixed number of steps for a variable-length list.

## What would actually need to change (a concrete plan, not fully verified against every call site — read each file before editing)

1. **`src/staged-workflow/contracts.ts`**: add a new `VariableKind` member (e.g. `'messages'`) and a corresponding `VariableValue` variant, e.g. `{ kind: 'messages'; messages: Array<{ role: 'user' | 'assistant'; text: string }> }`. Update `valueText()` in `contentRunner.ts` (the `switch (value.kind)` there is exhaustive — TypeScript will force this) to render it sensibly as input context for other stages, even though nothing currently needs to consume a `messages` value as an *input*.
2. **`src/staged-workflow/compileTurnPlan.ts:48`**: add `'messages'` to the `kinds` array. Line 187's `generate-content` check needs to allow `step.output === 'text' || step.output === 'messages'` (or more generally, a step-declared allow-list) — read the surrounding function fully first; there may be other places that assume `'text'` is the only generate-content output (search the file for `'text'` and `output.kind` before committing to the exact condition).
3. **`src/staged-workflow/scheduler.ts`**: `StagedSchedulerAdapters['generateContent']`'s return type is `Promise<string>` — decide whether to (a) keep it string-returning and have `outputValueForStage` (or a new wrapper called just before it) JSON-parse and validate the raw string into a `messages` value when `stage.output.kind === 'messages'`, or (b) widen the adapter's return type to `Promise<string | VariableValue>` like `executeAction` already is. Option (a) is probably less invasive — it keeps the LLM-facing contract uniform (every content stage still just returns text; the *content* of that text is a JSON blob for this one stage type) and mirrors how the top-level plan call already works (one LLM call returns a JSON string, parsed and validated by the caller, not the adapter). Check `planCall.ts` for that exact pattern before deciding — it's the closest existing precedent in this codebase for "one text completion, parsed as structured JSON."
4. **`src/staged-workflow/contentRunner.ts`**: `stagedContentPrompt()` currently always ends with "Return only the requested draft text. Do not emit JSON..." — this instruction must flip for a `messages`-kind step: it needs to request a JSON array (or object) matching `assistant.chat`'s exact shape, and the caller (wherever the parse/validate from step 3 lands) needs to enforce the same alternation/count rules `compileReply.ts`'s `assistantChat()` already enforces for `actions-v1` — reuse that validation logic if it can be shared, don't re-derive it from scratch. Check whether `compileReply.ts`'s validation is easily extracted/reused, or whether staged mode needs its own copy (if so, keep them behaviorally identical and comment why they're duplicated).
5. **`src/staged-workflow/recipeInventory.ts`**: promote `assistant.chat` to `advertised: true`/`executor-backed`, update `initiators` to `['model', 'direct-user']` (already partially done — check current state, this session already updated the entry's initiators and comment while explaining why it's *not yet* ported; re-read the entry before editing), add to `whitelistedActionRecipeIds`, add a `stagedRecipeDefinitions()` branch with a single step: `{ key: 'messages', kind: 'generate-content', output: 'messages', inputs: ['context'], instruction: 'instructions', generations: 0 }` followed by `{ key: 'receipt', kind: 'execute-action', output: 'receipt', inputs: ['messages'] }`. `validate()` should mirror `note.write`'s (`assertCharacter` for `actorId`/`args.ownerId`, require they match — "a character can only use their own assistant app").
6. **`src/staged-workflow/stagedActionAdapter.ts`**: new `assistant.chat`/`receipt` branch — read the `messages`-kind input record, call `bridge.execute` with the `assistant.chat` intent (owner, messages), check `result.type === 'assistant.chatted'`, return `{ kind: 'receipt', operationId, receiptId: \`chat:${result.chatId}\` }`.
7. **`src/app/useGraphRun.ts`**: the `chat:` receipt prefix needs adding to the "adapter already recorded it, nothing to render" check in the `useStagedActions` branch (same spot `note:`/`bank:` were added this session — search for `item.receiptId.startsWith`). `liveSimulatedAiChatCommits`/`commitSimulatedAiChats` wiring already exists in that branch (added this session alongside `note.write`'s staged port) — confirm it still fires correctly for this new path; it should, since it's the same `actionBridge`/adapter, just reached via a new recipe.
8. **Tests**: extend `contracts`-level tests if any exist for `VariableKind`/`VariableValue` exhaustiveness, `compileTurnPlan.test.ts` (check it exists and what it currently asserts about generate-content output kinds), `recipeInventory.test.ts` (advertised-list, definition-shape, validator — follow the exact pattern added for `note.write`/`bank.transfer` this session), `stagedActionAdapter.test.ts` (a committed-case test, and probably a malformed-JSON-from-the-model rejection case, given this is the first staged step whose raw LLM text is parsed as data rather than used verbatim). New Electron regression: extend `test/e2e/stagedBankingNotes.spec.ts`'s pattern (or a new file) with a staged-v1 turn whose plan includes an `assistant.chat` instance, and a fake `llm:chat-completion` handler that returns valid JSON for the `Stage: assistant.chat/messages` prompt — verify the delivered conversation lands in `session.ui.chatGpdChatsByCharacter` (same lookup-by-iterating-values pattern used in `test/e2e/assistantChat.spec.ts`, since the runtime character id is a synthesized `storybookCharacterId(...)`, not the raw storybook id).
