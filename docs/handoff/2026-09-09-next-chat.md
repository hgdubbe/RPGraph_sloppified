## Architectural Direction

- Capture typed reusable GH (history), LM (latest input/messages), OC (authoritative overall context), I (stage-specific instructions), plan, drafts, visual briefs, artifact references and receipts.
- Keep scene intent, arbitrary presentation beat order and execution dependency order separate. Do not impose a fixed narration/action/subaction template.
- Generate each creative component in its own selected-input LLM call. Store exact input revisions and provenance.
- Lock actor, recipient, owner, account, amount and destination before creative writers run. Prose must not overwrite authority.

- Images can exist only as attachments without a separate visible generation beat. Generated artifacts must be reused when retrying only delivery.
- Start sequentially with bounded calls/generations/continuations and cancellation. Durable receipts/recovery must precede enabling regeneration of effectful structured turns.
- Cover all action families eventually, not just WhatsUp/images: social posts/comments, voice, notes, simulated assistant, banking, choices/info and authorized controls. Only advertise actually registered, tested capabilities.

## S1-S3: What Exists Now

### Contracts

[src/staged-workflow/contracts.ts](../../src/staged-workflow/contracts.ts)

- `TurnScope`: saveId, branchId, turnId.
- `VariableRef`: id, revision, kind, full scope. Scope is in every reference to reject identical id/revision collisions across turns.
- Kinds: text, facts, entity, artifact, receipt, plan. Artifact/receipt values contain IDs rather than binary payloads.
- `VariableRecord`: value, exact input refs, context/stage producer, authoritative/observed/generated provenance, system/shared/character audience, draft/turn/promoted retention.
- `TurnContext`: scope, catalogRevision, GH/LM/OC and instruction refs.
- Stage kinds: retrieve, plan, generate-content, execute-action, compose, await-user.
- Typed dependency categories: content, artifact, state, observation, presentation, user-input.
- `TurnPlan`: version `staged-v1`, context, stages, ordered beats, lockedArguments, limits.
- `assertStageKind` and `assertReferenceType` are narrow internal guards, NOT a parser for untrusted model plans.

### Variable Store

[src/staged-workflow/variableStore.ts](../../src/staged-workflow/variableStore.ts), [nine foundation tests](../../src/staged-workflow/variableStore.test.ts)

- Turn-local store; detached copies on write/read/ref return prevent caller mutation.
- Exact revision tracking and scope/type checks. Default hard budgets: 2048 records, 2,000,000 serialized characters.
- Input refs must exist and not be invalidated. An output cannot widen a private input's audience.
- Stage-produced output cannot be marked authoritative. Context-source authority remains a trusted application responsibility.
- Changing an input invalidates dependent uncommitted records transitively. Committed receipts stop propagation so already-observed outcomes remain usable.
- Only latest valid receipt revisions can be marked committed; committed receipts cannot be revised.
- Rejected writes do not consume a revision. Existing variable IDs cannot change kind.
- Old/invalidated revisions remain readable for inspection. Consumers must explicitly reject invalidated inputs before generation/execution.
- Persistence, promotion authorization, pruning, store serialization and effect replay are NOT implemented.

### Context Builder

[src/staged-workflow/contextBuilder.ts](../../src/staged-workflow/contextBuilder.ts), [six context tests](../../src/staged-workflow/contextBuilder.test.ts)

`captureTurnContext({scope, catalogRevision, read})` calls the trusted application reader once, detaches its snapshot, and returns `{store, view, visualInputs}`.

- Input: workflow nodes, message records, latest-message IDs, optional per-message visibility, trusted facts, summaries and stage instruction text.
- Reuses `storyCharactersFromNodes`, `normalizePhoneName`, `formatChatHistory`, `bankingBalanceForCharacter` and `bankTransactionsForCharacter`.
- `view(characterId)` is character-specific; `view()` is a trusted system view. Views are cached but returned refs are detached. View variable IDs are namespaced by audience to avoid collisions.
- GH contains included non-error history except latest messages. LM contains latest messages. Each fact preserves `message:<id>` source and formatted text, including existing annotation handling. Formatting uses only already-filtered linked messages.
- Phone participants must resolve uniquely using existing normalized names. Duplicate name-keyed casts are rejected before deriving banking context. Unknown participants fail closed for character history.
- Non-phone narration needs explicit application visibility; without it only system sees it. Explicit visibility cannot broaden access to private phone content.
- Mixed RP records containing an inaccessible embedded phone exchange are withheld whole; do not guess which prose fragments are public.
- Social DMs, embedded social messages, notes and simulated-assistant records are currently withheld from character views. Their safe app-specific projections must be added with their recipes/rollout, not silently exposed.
- OC includes only visible trusted facts, the viewer's own storybook profile/appearance, and own calculated USD bank balance with transfer source message IDs. System can see all characters. Balance is captured state, NOT transfer authorization; effect boundaries must refresh state.
- Summaries are separate refs with generated provenance, never merged into OC. Instructions are separate observed text refs.
- `visualInputs(characterId, draftRef, sceneRef)` requires visible non-invalidated text refs, returns `[appearanceOnlyRef, sceneRef, draftRef]`. Scene instructions carry clothing/setting/framing/intended event; actual draft stays an exact separate revision. Visual context excludes personality and finances.
- Scene completeness and locked argument checks still belong to planner/recipe validation. No gallery-access expansion, arbitrary trusted-fact extraction from prose or model-generated authority was added.
- Everything is still isolated from live generation and editor UI. S3 checked means pure foundation complete, not that every app knowledge adapter exists.

### Boundaries To Consider During S4

These are implementation limits/follow-up design concerns, not claims that all are observed user-facing bugs:

- Current TS contracts accept internal typed data; never cast arbitrary model JSON straight into them or into the store.
- Plan outputs name future variables while the store holds realized revisions. Explicitly define and validate producer/output bindings and how future refs become actual revisions. Do not require nonexistent future outputs to be in the store already or fabricate them as committed records.
- Variable-store APIs are trusted backend APIs, not a permission boundary for arbitrary renderer/model writes. Promotion and observed-vs-generated provenance policies need appropriate owners.
- A revision that consumes its own prior revision may interact with invalidation; define refinement semantics before using this pattern in the scheduler.
- Captured context views are trusted snapshots. Reads allow old revisions for inspection; selectors/runner must check invalidation and never silently substitute a newer draft.
- Context banking uses existing application math/records. It does not implement new account permission or amount validation.
