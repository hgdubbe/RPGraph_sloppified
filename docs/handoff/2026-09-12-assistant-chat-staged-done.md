# RPGraph Continuation Handoff — assistant.chat on staged-workflow-v1 (done)

## Status: Done

Implemented the plan from `docs/handoff/2026-09-12-assistant-chat-staged.md` in full. `assistant.chat` is now the last `actions-v1` family ported onto `staged-v1`, closing out the S10 action-family rollout end to end. Nothing was left partially done; all steps in that handoff's numbered plan were completed as described, with two small deviations noted below.

## What changed

1. **New shared validator** — `src/actions/assistantChatMessages.ts`: extracted the alternating-role/shape validation (2-8 entries, starts with `user`, exact field set) out of `compileReply.ts`'s `assistantChat()` into `validateAssistantChatMessages(raw, { maxTextLength, fail })`, a pure function taking a `fail(path, message): never` callback so each caller keeps its own error type/paths. `compileReply.ts`'s `assistantChat()` now calls it and wraps `fail` around the existing `reject()` helper — same error paths/codes/messages as before, verified by the unmodified `compileReply.test.ts` suite passing unchanged. This is the "reuse rather than re-derive" the exploratory handoff flagged as worth checking.
2. **`src/staged-workflow/contracts.ts`**: added `'messages'` to `VariableKind` and a `{ kind: 'messages'; messages: Array<{role, text}> }` `VariableValue` variant. The only place needing a new `case 'messages':` arm was `contentRunner.ts`'s `valueText()` (confirmed by grepping the whole directory for `case 'plan':` — it's the only exhaustive switch over `VariableValue.kind`).
3. **`src/staged-workflow/compileTurnPlan.ts`**: `'messages'` added to the `kinds` validation list; the `generate-content` output check now accepts `'text' | 'messages'` via a small `generateContentOutputKinds` allow-list constant, replacing the old text-only check. No other `'text'`-specific assumptions existed elsewhere in the file (confirmed by reading the full file, not just grepping the one flagged line).
4. **`src/staged-workflow/scheduler.ts`**: took option (a) from the exploratory handoff — `StagedSchedulerAdapters['generateContent']` stays `Promise<string>`; `outputValueForStage()` gained a `stage.output.kind === 'messages'` branch that runs `parseJsonReply` (the same "one text completion, parsed as structured JSON" helper `planCall.ts` already uses for the plan itself) on the raw string, then `validateAssistantChatMessages` on the parsed value, throwing a scheduler-level `Error` on either JSON or shape/alternation failure. This keeps every content-stage adapter uniformly text-in/text-out; only the *interpretation* of that text differs per output kind.
5. **`src/staged-workflow/contentRunner.ts`**: `valueText()` got a `case 'messages':` arm (renders as `role: text` lines, for use as upstream input context — nothing consumes a `messages` value as an input today, but the switch has to be exhaustive). `stagedContentPrompt()` now branches its trailing instruction line: the existing "return only draft text" line for `text` output, a new explicit "return a JSON array of 2-8 alternating `{role, text}` objects" line for `messages` output.
6. **`src/staged-workflow/recipeInventory.ts`**: `assistant.chat` promoted to `advertised: true` / `implementation.status: 'executor-backed'`; added to `whitelistedActionRecipeIds`; new `stagedRecipeDefinitions()` branch with the exact two-step shape the exploratory handoff specified (`messages` generate-content step outputting `'messages'`, then a `receipt` execute-action step consuming it); `validate()` mirrors `note.write`'s owner-must-match-actor check with an "own assistant app" message. Comments updated in place (the old "not yet staged-executor-backed, here's why" comment on the inventory entry now explains what *was* built, not what's missing).
7. **`src/staged-workflow/stagedActionAdapter.ts`**: new `messagesInput()` helper (kind-based lookup, like the existing `artifactInput()` — reliable here since `assistant.chat`'s recipe has exactly one `messages`-kind input, unlike `note.write`'s two same-kind `text` inputs that needed positional lookup) and a new `assistant.chat`/`receipt` branch calling `bridge.execute` with the `assistant.chat` intent, checking `result.type === 'assistant.chatted'`, returning `chat:<chatId>` as the receipt id.
8. **`src/app/useGraphRun.ts`**: added `chat:` to the staged-branch's "adapter already recorded it, nothing to render" receipt-id prefix check (was `social:`/`note:`/`bank:`, now also `chat:`). The `liveSimulatedAiChatCommits` accumulator and its before-`commitCollectedTurn` commit call already existed from this session's `actions-v1` work and needed no changes — confirmed, not assumed, by tracing the same code path the exploratory handoff pointed at.

## Deviations from the exploratory plan (both minor, noted for the record)

- The exploratory handoff's point 3 flagged two options for the scheduler change and recommended (a) as "probably less invasive"; that recommendation held up and was used as described, with no need to fall back to (b) (widening the adapter's return type).
- The exploratory handoff's point 4 asked whether `compileReply.ts`'s validation was "easily extractable" — it was, cleanly, with no behavior change and no duplication left behind (contrary to the handoff's fallback assumption that duplication with a comment might be necessary).
