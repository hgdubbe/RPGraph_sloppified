## Investigation finding (same shape as the earlier "voice lesson")

Before writing code, checked what `note.write`'s recipe-inventory entry (`initiators: ['direct-user']`, `compatibility-only`) actually corresponds to in the real codebase. Unlike banking — which genuinely had no model-authored path before M7 — notes already work for **both** initiators today via two independent legacy mechanisms:
- Model-authored: a `create_note` prompt-command ([promptCommands.ts](../../src/nodes/shared/promptCommands.ts)), parsed in `useGraphRun.ts`.
- Direct-user: the Notes-app UI submits `{createdPhoneNotes:[...]}` as a `directActionOnly` graph run ([directAppActions.ts](../../src/chat/directAppActions.ts), [useDirectAppActions.ts](../../src/app/useDirectAppActions.ts)).

So the actual gap was narrower than "make this possible at all": it was "let the model author a note through the new `actions-v1`/staged-executor JSON protocol, with catalog validation and H7 journal coverage" — the same class of upgrade M7 gave banking, but for a feature that wasn't broken or missing beforehand.

## choice.information / ui.control (added immediately after, same session) — no new canonical action needed

Investigated per the recipe inventory's own flagged uncertainty. Conclusion: **neither needs a canonical action at all.** Both `choice.information` (choices, info boxes, progress bars, context-capacity bars) and `ui.control` (tab/player controls) are pure local rendering / UI-state operations (`appendMessage` with `includeInHistory: false`, or `selectChatPanelView`/`selectChatCharacter`) with **no backend effect** — nothing to validate against a catalog, nothing to execute, nothing to journal. Confirmed by reading `src/chat/outputActions.ts` and the `appendOutputActionUiItem`/controls-handling code in `useGraphRun.ts`: unlike every other family this session, these already flow through a wholly separate, pre-existing "Output Actions" auxiliary prompt channel (a second, independent prompt output the graph can wire into the RP Output's `output-actions` handle) — orthogonal to both the legacy narrative text and the new `actions-v1` JSON envelope.

**The actual bug**: that auxiliary channel was silently dropped for both `actions-v1` and `staged-v1` protocol turns. Root cause, found by tracing why the data never reached rendering: `src/graph/executeGraph.ts:819` had `for (const handle of structuredActionContext ? [] : auxiliaryOutputHandles)` — added during this branch's own earlier actions-v1 work, on the (correct, for those handles) assumption that `highlighting-context`/`phone-message`/`social-media`/`autoplay` are made redundant by the JSON envelope. `output-actions` has no such equivalent and was wrongly swept into the same skip. Fixed by narrowing the skip to exclude `output-actions`:
```ts
for (const handle of auxiliaryOutputHandles.filter((candidate) => !structuredActionContext || candidate === 'output-actions')) {
```
In `useGraphRun.ts`, the existing controls/uiItems rendering code (previously only reachable from the legacy commit path, far below the `actions-v1` early return) was split into two reusable functions (`applyOutputActionControls`, `applyOutputActionUiItems` — kept separate, not merged, to preserve the legacy path's exact original message ordering: controls → chatMessages → uiItems) defined once, before the `useStagedActions`/`actionBridge` branches, and called from a new spot inside the `actionBridge && !directActionOnly` early-return block using a freshly-parsed `parseOutputActions(outputActionsText)` (the same auxiliary text already being computed for other purposes). `staged-v1` was deliberately left out of scope here too — it doesn't call `executeGraph` at all (`runLiveStagedTurn` is a separate content-composition engine with no auxiliary-handle concept), so there is no existing mechanism to "restore"; adding choice/control support there would be new feature work, not a family port.

New Electron regression: `test/e2e/outputActionsUi.spec.ts`, wiring a `write-text` node (a static-JSON source, no LLM call needed) into the output node's `output-actions` handle alongside an `actions-v1` narrative reply, and asserting the choice buttons render.

### A second, real, unrelated bug found and fixed along the way

Stress-testing `noteWrite.spec.ts` + `assistantChat.spec.ts` back-to-back (not the documented "first-test" Electron flake — a different, reproducible ~50-65% failure rate, order-independent, always a **silent empty-state timeout**, never a thrown error) surfaced a genuine pre-existing-pattern bug in this session's own new code:

1. **Commit ordering** (this session's own new-code bug): the actions-v1 model-authored early-return block called `commitCreatedPhoneNotes`/`commitSimulatedAiChats` *after* `commitCollectedTurn`, backwards from the established, battle-tested order already used by the legacy commit path a few hundred lines down (`commitSimulatedAiChats`/`commitCreatedPhoneNotes` called *before* `commitCollectedTurn`). Turn-autosave triggers off a `useEffect` keyed on the `turns` state changing (`App.tsx:2356`), gated by a ref (`lastTurnAutosaveIdRef`) so it never re-fires for the same turn id — so committing the note/chat store *after* the turn risks that effect capturing a snapshot before the update lands, permanently missing it for that turn. Fixed by matching the legacy order.
2. **A real, independent, pre-existing architectural gap**, exposed (not caused) by fix #1 reducing but not eliminating the race (~35%→~20% failure rate after #1 alone): `phoneNotesByCharacter`/`chatGpdChatsByCharacter` are plain `useState` with **no ref mirror**, unlike `turns` (which has `turnsRef`, updated synchronously alongside `setTurnsState` specifically to avoid this exact class of bug — see `useTurnRecordState.ts:72-75`). `currentSessionState()` (`App.tsx`, the function the autosave effect calls to build its snapshot) closed over the plain state values, which can still be one batching/render tick stale relative to a same-tick sequence of setState calls. Fixed by giving `phoneNotesByCharacter`/`chatGpdChatsByCharacter` the identical `useRef`-mirrored-setter treatment as `turns` (`useRoleplayPanelRuntime.ts`), and switching `currentSessionState()` to read the refs. This is a **general fix**, not scoped to actions-v1 — it protects the pre-existing legacy note/chat commit path too, which was presumably exposed to the same theoretical race (just apparently rare/unobserved there before now).

Verified via repeated stress runs of the same two-spec pair: 13/14 passed after both fixes (the one failure was fast, ~800ms, and matched the *actual* documented "Execution context was destroyed" flake wording exactly — confirmed by reproducing it in isolation immediately after, on an unrelated spec, on an unrelated line). Before fix #1: ~35% pass rate. After #1 only: ~80%. After #1+#2: ~93%, with the residual failures being the pre-existing documented flake, not this bug's signature (silent empty state).

## staged-workflow-v1 port: bank.transfer and note.write (added immediately after, same session)

**Correction from the user, applied here**: earlier framing (this doc included) treated `bank.transfer` as architecturally exceptional — worth calling out directly, since it turned out to be wrong. Investigated all three staged-v1 gaps (`bank.transfer`, `note.write`, `assistant.chat`) with the same uniform method, and it turns out `bank.transfer` was the *easiest* of the three to port: one creative field (`note`), fitting the existing single-text-output-per-step recipe shape exactly like `social.post`. Ported it and `note.write` (two creative fields — see below) to the shared staged executor; `assistant.chat` genuinely doesn't fit yet, for a specific, checkable reason, not by default deferral.

- [recipeInventory.ts](../../src/staged-workflow/recipeInventory.ts): `bank.transfer` and `note.write` promoted to `executor-backed`/`advertised: true`, `initiators` widened to `['model', 'direct-user']` (matching the actions-v1 finding that both already have real model-authored legacy paths). Added `stagedRecipeDefinitions()` branches for both, following `social.post`'s exact `generate-content` → `execute-action` two-step shape for `bank.transfer` (creative field: `note`, optional — dropped when blank, same as `actions-v1`), and a *three*-step shape for `note.write` (`title` and `body` are two separate `generate-content` steps, since the compiler's step model only supports one text output per step; the final `execute-action` step takes both as `inputs: ['title', 'body']` — multi-input `execute-action` steps already existed for the image-attachment case, so no new compiler infrastructure was needed). `note.write` only supports creating a new note in staged mode (no `noteId` locked argument) — updating an existing note isn't exposed here, matching `assistant.chat`'s pre-existing create-only scope; noted inline as a real, specific limitation, not a stand-in for "harder."
- `assistant.chat` stays `compatibility-only`, with the entry's comment now explaining precisely why: its creative content is a *variable-length* (2–8 message) alternating array, and today's staged content-generation step produces exactly one fixed text output — porting it needs either a new structured/repeating step kind in the compiler or a hardcoded exchange count that would understate the feature. That's a real, specific, checkable technical gap, not a "banking is special" style deferral.
- [stagedActionAdapter.ts](../../src/staged-workflow/stagedActionAdapter.ts): new `bank.transfer`/`receipt` and `note.write`/`receipt` branches, both following the existing adapter pattern (resolve catalog handles, call the shared `bridge.execute`, check the committed result's exact type, return a `bank:<operationId>` / `note:<noteId>` receipt). Added `textInputAt(inputs, index, label)` — a positional lookup, needed because `note.write`'s two text inputs (title, body) share the same `kind: 'text'`, unlike every other existing multi-input case here (`draft`+`attachment`), which could disambiguate by *kind* alone. Verified positional reliability by reading `scheduler.ts`'s `recordsFor`: `inputs` is built from `stage.inputs.map(materialized)`, preserving the recipe step's declared `inputs: [...]` order exactly.
- [useGraphRun.ts](../../src/app/useGraphRun.ts): the `useStagedActions` branch was missing the *exact same* two things the `actions-v1` branch needed fixing earlier this session — `commitCreatedPhoneNotes`/`commitSimulatedAiChats` calls (now added, in the same before-`commitCollectedTurn` order) and a `note:`/`bank:` case in the "adapter already recorded it, nothing to render" receipt-id check (alongside the existing `social:`/`message:` ones). Without these, a staged-v1 note or transfer would have committed the effect but silently dropped it from the visible turn/autosave — caught before it shipped, by inspection this time, not by a repeat of the earlier stress-test discovery.
- Tests: `recipeInventory.test.ts` (advertised-list, recipe-definition-shape, and validator cases for both — plus updated the "legacy command family stays unadvertised" assertions, since `bank_transfer`/`create_note` are now advertised and only `simulate_ai_chat` remains not), `stagedActionAdapter.test.ts` (one committed-case test each, including the blank-note-gets-dropped case for `bank.transfer` and the positional title/body disambiguation for `note.write`). New Electron regression [test/e2e/stagedBankingNotes.spec.ts](../../../test/e2e/stagedBankingNotes.spec.ts): one staged-v1 turn producing both a real bank transfer and a real phone note in the same plan, asserting both landed in the autosave and the effect journal ended empty.
