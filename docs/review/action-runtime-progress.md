## 2026-09-12: S8 First Slice — Retry Without Regenerating (Roadmap M10)

Delivers the first concrete piece of S8 durable recovery for staged turns: **retrying a failed staged turn no longer repeats a stage that already committed a real effect.** If a turn generates a real ComfyUI image, then fails on a later stage (say, the WhatsUp send after it), a retry reuses that already-generated image instead of paying for another generation. Scope was narrowed deliberately with the user before writing any code — this slice covers retry-without-regenerating plus both an automatic and a manual retry surface; full reconciliation (recovering a turn after an app restart) and action-preserving regeneration of *narrative* content remain later S8 work.

- **The mechanism:** [src/staged-workflow/scheduler.ts](../../src/staged-workflow/scheduler.ts)'s `runCompiledTurn` gained an optional `resume` option — a set of already-succeeded stage ids plus their realized outputs — seeded into the run's state before the main loop, so those stages are skipped entirely rather than re-executed. [src/staged-workflow/runLiveStagedTurn.ts](../../src/staged-workflow/runLiveStagedTurn.ts) exposes this as a `resume: StagedRetryState` option that bypasses planning/compiling altogether and reuses the exact same compiled plan and `VariableStore` from the failed attempt; every `run-failed` result now carries its own `retry: StagedRetryState`, built from the failed run's own `stages`/`outputs` (which already accumulate correctly across any number of resumes, so no extra bookkeeping is needed by callers).
- **Two retry surfaces, per explicit user request:** [src/app/useGraphRun.ts](../../src/app/useGraphRun.ts)'s staged branch first retries automatically, up to a new `stagedAutoRetryAttempts` setting (default 3, range 0-10, configurable in Settings → Run Reliability), reusing each failed attempt's `retry` state. Once that budget is exhausted, it awaits a user decision instead of failing outright — a persistent `stagedRetryPrompt` (exposed from the hook, rendered by `App.tsx` as a banner with Retry/Dismiss buttons) that resolves the same underlying resume path when clicked, or ends the run like any other failure when dismissed or the run is cancelled.
- **A UI placement bug caught before it shipped:** the app's only existing notification mechanism (`notifySystem`/the `graph-system-toast` element) turned out to render exclusively inside the Graph Mode toolbar tree — never inside `RoleplayStudioShell.tsx`, the actual Play Mode component staged turns run from. This is a pre-existing gap (Play Mode has no notification UI of its own at all), not something this slice introduced, but it meant an initial version of the retry banner silently never appeared during real usage despite every internal signal being correct. Fixed by rendering the banner directly inside `RoleplayStudioShell`'s children (visible above the chat/phone panes regardless of which surface tab is active) in addition to the existing Graph Mode toolbar location.
- Settings wiring follows the existing `maxReferenceImages`-style numeric-setting pattern exactly (`src/settings.ts`, `src/types.ts`, `src/dialogs/StudioDialogs.tsx`): a `validStagedAutoRetryAttempts` clamp (0-10), full load/save/validate round-trip, and a range-slider control under Settings → Run Reliability (chosen because that tab is already themed "Crash recovery and automatic retry").
- Tests: `scheduler.test.ts` (a new case proving a resumed run skips the content stage a prior failed attempt already completed, only retrying the previously-failed action stage), `runLiveStagedTurn.test.ts` (a new case proving `resume` skips both the plan call and the content draft call entirely on a real `runLiveStagedTurn` invocation). New Electron regressions [test/e2e/stagedRetry.spec.ts](../../../test/e2e/stagedRetry.spec.ts): two cases, both forcing the *second* of two image generations to fail once (ComfyUI generation is the only real effect in this app that's both IPC-based and therefore deterministically failable from a test — WhatsUp/bank/social/notes effects are plain in-memory state) — one with auto-retry enabled (recovers silently, banner never appears), one with it disabled (banner appears with the real error text, clicking Retry recovers) — both asserting ComfyUI was asked for exactly one photo per successful generation, never twice for the one that already succeeded.
- Verification: 438 vitest tests pass (was 436), `tsc -b`/ESLint clean, `npm run build` clean. **21/21 action-related Electron regressions pass together, twice in a row** (the existing 19 plus `stagedRetry` ×2 new); one run hit the already-documented `actionBaseline.spec.ts` navigation-context flake, confirmed unrelated by an isolated rerun passing both its cases cleanly.
- Still open (real S8 scope, not this slice): reconciling a turn that crashed the whole app mid-flight (this slice's resume state is in-memory only, held for the lifetime of the run's own async call — it does not survive a restart); action-preserving regeneration of narrative/creative content; branch semantics for continuation planning.

## 2026-09-12: Image Generation Works in Staged Mode (Roadmap M8, ComfyUI Runner Extraction)

Closes the roadmap's other standing image-generation gap: `image.generate` now works end to end on `staged-v1`, not just `actions-v1`/legacy. This was blocked purely by wiring, not by anything in the staged compiler/scheduler/recipe stack — `image.generate` has been an advertised, executor-backed staged recipe since the S6 era; it just had no working runner behind it in staged mode.

- **Root cause, confirmed by reading, not assumed:** `executeGraph.ts`'s ComfyUI generation logic (`createComfyImageForCharacter`) lived entirely inside `executeGraph`'s own closure, publishing itself to the rest of the app only via an `onImageRunnerReady` callback fired from inside a graph run. Staged mode's `useGraphRun.ts` branch never calls `executeGraph` at all (it calls `runLiveStagedTurn` instead), so `imageRunner` stayed `undefined` for the entire staged turn, and `image.generate` stages failed with "the graph image-generation adapter is unavailable" whenever they were attempted (which the earlier assistant.chat/notes/banking work never exercised, since none of those turns touch images).
- **Fix: extracted, not rewritten.** [src/graph/comfyImageRunner.ts](../../src/graph/comfyImageRunner.ts) is the exact same logic — phone-owner/LoRA-character resolution by name or id, the actual ComfyUI call, generated-image captioning, and ensuring the result lands in the owner's Storybook — moved into a `createComfyImageRunner(options)` factory that takes its dependencies (`getNodes`, `connections`, `providerHealthById`, `llm`, `updateRuntimeNode`, `onComfyGenerationActive`, `signal`) as parameters instead of closing over `executeGraph`'s internals. `executeGraph.ts` now just calls this factory with `getNodes: () => nodes` (the exact same run-start snapshot it always used, preserving identical behavior — verified by the pre-existing `structuredActions.spec.ts` image-generation case still passing unchanged). `resolveCreateImageCharacterByName`/`CreateImageCharacterNameResolution` moved with it; `executeGraph.ts` re-exports both so the existing external import in `validation.fixtures.test.ts` didn't need to change.
- **The actual staged-mode fix:** [src/app/useGraphRun.ts](../../src/app/useGraphRun.ts) now builds `imageRunner` eagerly at declaration time via `createComfyImageRunner({ getNodes: () => nodesRef.current, ... })`, instead of leaving it `undefined` until `executeGraph`'s callback fires. For every existing protocol, `executeGraph` still runs afterward and immediately overwrites this with its own run-scoped instance — byte-for-byte the same behavior as before this change. For staged mode, which never reaches that call, the eager instance is what actually runs `image.generate`. No staged-workflow file needed to change at all: `image.generate`'s recipe/adapter/compiler wiring was already correct and waiting on a working runner.
- New Electron regression: [test/e2e/stagedImageGeneration.spec.ts](../../../test/e2e/stagedImageGeneration.spec.ts), mirroring `stagedBankingNotes.spec.ts`'s fake-plan pattern and `structuredActions.spec.ts`'s `withImage: true` ComfyUI IPC mocking — a two-instance staged plan (`image.generate` → `whatsup.message-with-artifact`, the artifact wired as the second instance's `attachment` input, exactly matching how the compiler already supports multi-input `execute-action` steps), asserting the delivered WhatsUp message actually carries the generated image in the autosave timeline and the effect journal ends empty.

## 2026-09-11: Voice Messages — Live (Roadmap M6, First Family)

First S10 family after social (M5): `voice.message` is now advertised and live for both `actions-v1` and `staged-v1`. Chose voice over banking for this slice because investigation showed it needed far less new infrastructure than the inventory's stale design assumed — see below.

- **Key discovery that shaped the whole design**: voice-message audio synthesis in RPGraph is fully lazy/client-side — `appendPhoneMessage` only ever sets a boolean (`MessageRecord.phoneVoiceMessage`); the actual TTS clip is generated on demand only when a user clicks play (`src/chat/useDialogueVoice.ts`'s `getOrGenerateClip`, wired through `PhoneVoiceMessage.tsx`'s `onGenerateClip`). This means a "voice message" is not a distinct effect needing its own artifact/provider-call plumbing in the action executor — it is exactly a WhatsUp `messenger.send` with one extra rendering flag. The recipe inventory's pre-existing `voice.message` entry had assumed otherwise (a locked `voiceProviderId` argument and a `voiceDirection` creative field that correspond to nothing real in the codebase); both were removed as part of promoting the recipe, mirroring the M5 pattern of correcting stale/speculative design once a family is actually implemented.
- [src/actions/contracts.ts](../../src/actions/contracts.ts): `MessengerSendAction` gained an optional `isVoiceMessage?: boolean` field — reusing the existing canonical action rather than adding a new one, since the underlying mechanism is identical to a plain WhatsUp send.
- [src/actions/schema.ts](../../src/actions/schema.ts): `messengerSchema` gained an optional `isVoiceMessage: boolean` property. The llama.cpp provider-projection alternatives (`textOnlyMessengerSchema`/`attachedMessengerSchema`) were updated carefully: `attachedMessengerSchema` previously spread `messengerSchema.properties` with an implicit "all keys required" default, which would have wrongly forced every attachment-carrying reply to also declare `isVoiceMessage` — fixed by passing an explicit `required` list. Regenerated `electron/providers/actionReply.schema.json` via `npm run actions:schema`.
- [src/actions/compileReply.ts](../../src/actions/compileReply.ts): the `messenger()` compiler validates `isVoiceMessage` as an optional boolean and sets it on the compiled action only when `true` (an explicit `false` is dropped, matching how `attachment` is only present when supplied).
- [src/actions/executionRegistry.ts](../../src/actions/executionRegistry.ts): `MessageDeliveryRequest`/`messenger.sent`'s `ActionResult` variant both gained `isVoiceMessage?: boolean`; threaded through the `messenger` execution definition without adding it to the adapter-ack `resultSchema` (the flag is app-side rendering metadata, not something the adapter needs to echo back for validation).

2. Build catalogs from authoritative storybook/session state, including actual image access and provider availability. The current compiler accepts a trusted application-supplied catalog; no production catalog builder is wired yet.
3. Recheck availability/access at the effect boundary, especially after asynchronous generation. Successful preflight is not a durable authorization or proof that state cannot change.
4. Connect a single execution owner and adapt direct/legacy operations behind an explicit opt-in workflow boundary. Never execute both the compatibility path and the new runtime for one operation. Existing legacy helper behavior must stay isolated.
5. Implement result/receipt contracts, artifact storage and same-result phone/RP rendering. Compilation of dependencies alone does not prove that a generated image reaches a recipient; H5's deterministic provider/store tests and live integration are still required.
6. Only WhatsUp and existing character references are supported in this initial compiler. New contacts, other apps, advanced result selection, voice payloads and broader action types need explicit contracts rather than inferred support. Generated inline attachment ownership is restricted to the sender until cross-owner access semantics are defined.
7. The application must supply globally scoped operation IDs; the compiler checks uniqueness within one plan only. No execution, retries, persistence, crash recovery or exactly-once guarantee is implemented here. H7 remains open.

No UI or live-provider tests were run for this dormant compiler-only step. Prior Electron results remain historical, not evidence of an enabled action runtime.
